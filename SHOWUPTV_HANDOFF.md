## How the site works (as of 2026-10-05)

1. **Page:** showup.tv is a Next.js app behind Cloudflare. Plain urllib or `websockets` requests get 403. The page needs impersonation (`curl_cffi`, Chrome or Safari target; **Firefox gets 403**). Profile data is in `__NEXT_DATA__` at `props.pageProps`:
   - `broadcastData.broadcast`: `host.id`, `host.username`, `aliasStreamKey`, `loadBehaviour`, `broadcastAddress.type`, `imageUrl`
   - `broadcastData.profile.about`: `name` (display name), `description`
   - `serverData.streamServers.EDGE[]`: `{address, appName}`
   - Profile URLs: `/<username>` and `/en|pl/<username>`. Usernames match `[\w-]+` (e.g. `-LOVE-`, `55442`) and are **case-insensitive** in URLs (`/martynkaaa` serves `Martynkaaa`), so the extractor takes `id`/`uploader_id` from the page's `host.username`, not from the URL.
2. **Media transport:** nothing standard (no RTMP, HLS or DASH). The player speaks Softvelum "Storm v2" over WebSocket: `wss://<edge>/storm/v2/live` (port 443). JSON text frames:
   `clientHandshake` -> `serverHandshake`, `appInfo` -> `appAuthRequest {secret: null}` -> `appAuthResult` -> `subscribeRequest {streamKey: aliasStreamKey}` -> `subscribeResult {streamState, streamList[{streamKey, streamInfo{label,width,height,bitrate}}]}` -> `playRequest {streamKey, subscriptionKey: alias, packetizer: 'mse', accessPoint: 0}` -> `playResult` -> then **binary frames** that concatenate into valid fragmented MP4, interleaved with `playbackProgress` text frames (~every 0.35 s). The client pings (`{"packetId":"ping"}`) every 30 s.
3. **The server checks the handshake.** `protocolVer` must be `1` (2 gives `protocolMismatch`). Dropping the `environment` or `capabilities` fields made the server close the socket with a normal 1000 close during the handshake. The full set in `ShowupStormSession._handshake` is what works. The capabilities advertise only H.264 and AAC, which is why every stream seen was H.264 + AAC-LC.
4. **Access:** anonymous playback works. `appInfo.playbackSettings.tokenRequired` was `false`, the handshake sends `userId: null`, no session value feeds the Storm player, and the `accept_rules` cookie (used by the 2022 PR) is not needed.
5. **Cloudflare rules observed on the edge WebSocket upgrade** (the traps that cost the most time):
   - Needs a browser-like `User-Agent` **and** an `Accept` header. `Origin` is not needed. Cookies are irrelevant. Missing either gives 403.
   - yt-dlp's default headers satisfy this through its own `websockets` request handler (Python TLS stack, no impersonation). Probing with the bare `websockets` library, `curl_cffi` `ws_connect`, or a `curl/x` UA returned 403 in various combinations. Always test through `YoutubeDL.urlopen`.
6. **Dead ends (don't retry):**
   - The edge also serves an "HLS" playlist (`storm_hls/v2/live/<key>.m3u8?link=...`, a 1-segment VOD playlist pointing at a `.mp4`). That mp4 is behind a Cloudflare managed challenge, or returns 2 bytes then stalls. Not usable.
   - `WebSocketFragmentFD` (`websocket_frag`) cannot send the handshake and writes text frames into the output. Not usable.
   - `jc0N.showup.tv` is the "CallistoRTC" WebRTC publisher and app socket, unused.

## Design

- **Extractor** (`showuptv.py`): fetch the page with `impersonate=True, require_impersonation=True, expected_status=404`, parse `__NEXT_DATA__`, handle states, open a short Storm session to subscribe, and build formats from `streamList`.
  - `id`/`uploader_id` = username. `uploader` and `title` = `about.name` (falls back to the username). `channel_id` = numeric `host.id`. Also `description`, `thumbnail`, `age_limit` 18, `is_live` True.
  - Formats: `protocol: 'showup_live'`, `url` = the working `wss://` edge, `ext: mp4`, codecs, and `downloader_options` = `{stream_key, subscription_key, fallback_urls[all edges]}`.
  - Core appends a timestamp to live filenames, so repeat recordings don't collide.
- **Downloader** (`ShowupLiveFD`): open a *fresh* session (the extractor's socket is not carried over), connect before creating the file, write binary frames only, ping every 30 s, then remux.
  - Ends cleanly on `playbackStop`, a `subscribeUpdate` whose `streamState` isn't `PUBLISHED`, a closed or stalled connection (once bytes exist), or Ctrl+C when `is_live`.
  - Remux: `ffmpeg -c copy -movflags +faststart` in place. If it fails, the raw file is kept with a warning. The raw concatenated fMP4 has no index or duration, so players can't seek.
  - Edge fallback applies only before any media is received.
- **No mid-stream reconnect, by design.** Tested: two sessions concatenated into one file remux to ~9.5 s instead of ~16 s with non-monotonic DTS, because each session restarts timestamps and sends a new init segment. Joining sessions would need separate segment files plus ffmpeg concat. Not built, and not recommended; the usual approach (matches upstream cam extractors) is one file per session and an outer re-run.

## States (observed)

| State | How it appears | Behaviour |
|---|---|---|
| Online | 200, `loadBehaviour: ONLINE`, `aliasStreamKey` set, address type `PUB` | Extracts |
| Offline | 200, `loadBehaviour: OFFLINE`, alias `null` | `UserNotLive` (works with `--wait-for-video`) |
| Nonexistent | HTTP 404, `broadcastData.error.status == 404` (Polish message) | Expected error "Broadcast for user ... was not found" |
| Private show (performer in one) | Public profile reads OFFLINE; homepage `prv_group_list` entries have `type: 'PRV'` | Falls out as `UserNotLive` |
| Group show (`isGroup: true`) | Streams publicly | Works, recorded successfully |
| Non-`PUB` address type | **Never observed** | Expected error "private or group show" (defensive guess) |
| Any other `loadBehaviour` | Never observed | Expected error "Broadcast is not available (state: X)" |

## Environment and testing

yt-dlp needs optional dependencies at runtime: `curl_cffi` (`>=0.5.10,!=0.6-0.9,<0.17`) and `websockets`, plus ffmpeg for the remux. The system Python in this environment has neither `pytest`, `ruff`, `autopep8`, nor these libraries. A throwaway venv was used (lives in the old session scratchpad, so recreate it):

```
python3 -m venv /tmp/showup-venv
/tmp/showup-venv/bin/pip install curl_cffi websockets pytest pytest-randomly "ruff~=0.16.0" "autopep8~=2.0"
cd /home/mix/yt-dlp
/tmp/showup-venv/bin/python -m yt_dlp -F https://showup.tv/<online-user>   # get one from https://showup.tv/ (online list)
/tmp/showup-venv/bin/python -m pytest test/test_showup.py test/test_all_urls.py -q
/tmp/showup-venv/bin/ruff check yt_dlp/extractor/showuptv.py yt_dlp/downloader/showup.py test/test_showup.py
/tmp/showup-venv/bin/autopep8 --diff yt_dlp/extractor/showuptv.py yt_dlp/downloader/showup.py test/test_showup.py
```

Rules of thumb learned:
- Run yt-dlp from a scratch directory or pass `-o`, or it drops the recording in the current directory (this once put an mp4 in the repo root).
- A Claude Code safety check blocks `rm` with globs after `cd`. Avoid deletion commands; use `mv` or fresh directories.
- Performers go on and offline constantly. Pick a live one from the homepage `__NEXT_DATA__` (`props.pageProps.homeListData.list[].isOnline`) each time.
- Static analysis aid: the player JS is `/_next/static/chunks/pages/_app-*.js`; Storm strings include `STORM_WEBSOCKET_HARNESS`, `playbackLinkingPacket`, `PLAYER_PROTOCOL_VERSION`.

## Known fragility

- Relies on undocumented protocol details and Cloudflare header rules (see above). If extraction suddenly gives 403s or the socket closes with 1000, rerun the probe through `YoutubeDL.urlopen` and compare the handshake with the player JS.
- Needs `curl_cffi`. Without it the extractor stops with yt-dlp's "no impersonate target" error. A custom `--user-agent` or a stale browser `cf_clearance` cookie gives 403, and the extractor explains this.
- `ShowupLiveFD` uses the private `_hook_progress` (like other downloaders). `ShowupStormSession` is shared between extractor and downloader, which is unusual for this codebase.
- Upstream acceptance is doubtful (reverse-engineered protocol, optional-dependency requirements, new downloader).
